# dmdebug上位机

用于 STM32H723 三路 FDCAN 电机工程的串口调试工作台。提供 Windows 桌面程序和免安装单文件网页，支持设备发现、状态与参数查询、位置/底盘速度命令、实时曲线、CSV 导出和收发记录。

- 配套下位机：[HITSZ-WTRobot/FDCAN_DM_TEST](https://github.com/HITSZ-WTRobot/FDCAN_DM_TEST)。
- 串口契约：[设备控制协议 v2](https://github.com/HITSZ-WTRobot/FDCAN_DM_TEST/blob/main/SERIAL_PROTOCOL.md)。
- 联调与调参：[电机通信检查与调参步骤](https://github.com/HITSZ-WTRobot/FDCAN_DM_TEST/blob/main/MOTOR_TEST_GUIDE.md)。
- 详细使用说明：[web/README.md](web/README.md)。

## 支持的设备

| 总线 | 控制单元 | 单位与控制方式 |
|---|---|---|
| FDCAN1 | 四台伸缩 DM-S3519、两台关节 DM-J4340P | 伸缩为绝对 mm，关节为绝对 deg；下位机 S 曲线规划、电机内部 MIT 跟踪 |
| FDCAN2 | 四轮 DM-S3519 全向底盘 | 车体系 vx/vy 为 m/s，wz 为 deg/s；电机内部速度环 |
| FDCAN3 | 两台独立 M2006/C610 | 减速后输出轴绝对 deg；下位机轨迹速度前馈、位置 PD 和速度 PID |

共九个控制单元、十二台电机。上位机负责交互与协议，不承担电机实时控制，也不修改 CubeMX 外设配置。

## 运行入口

### 单文件网页

使用当前 Chrome/Edge 打开仓库中的 [web/index.html](web/index.html) 或 [web/串口.html](web/串口.html)。两份文件由同一源码生成，JS/CSS 已内联，不需要启动开发服务器。

选择“浏览器串口”，点击“连接固件”并授权实际串口。浏览器须支持 Web Serial 和 `Promise.withResolvers`，建议使用当前版本 Chrome/Edge（124+）。GitHub 的源码预览页不是串口运行入口，需要将网页下载到本地后打开。

### Windows 桌面

从源码执行下文的 `npm run build:all` 后，运行项目根目录的 `DMDebugStation.exe`，选择“桌面原生串口”及对应 COM 端口。需要 Microsoft Edge WebView2 Runtime。EXE 不纳入 Git 历史，本仓库不承诺已发布可下载的二进制 Release。

串口固定为 **115200 baud、8N1、无流控**。不要让多个程序同时占用同一端口；“协议演示 · 无硬件”仅供明确选择的演示，不是串口失败时的自动后备模式。

## 首次联调

1. 支撑机构、架空底盘四轮，确认硬件急停和安全空间；先保持所有设备失能。
2. 连接固件，依次确认“端口打开”“固件握手”“电机反馈”；端口打开不代表电机在线。
3. 逐台点击“刷新状态与参数”，确认反馈新鲜、有效反馈计数增长、零点建立且无故障；底盘检查四轮状态。
4. 一次只明确使能一台，发送已确认安全的小目标，依据新反馈判断使能与到位，不以 ACK 代替执行完成。
5. 测试结束先失能、核对新反馈并按现场流程隔离动力，再断开串口。

详细的串口按钮顺序、单位、故障恢复见配套的[联调步骤](https://github.com/HITSZ-WTRobot/FDCAN_DM_TEST/blob/main/MOTOR_TEST_GUIDE.md)。串口工作台的MIT/PID查询仍为只读；新增独立“Ozone调参”功能页，通过Windows桌面TCP后端直接读写实际控制器RAM，不增加串口操作码或固件暂存区。

## 只读手柄输入诊断

打开 `DMDebugStation.exe` 的“输入诊断”即可使用新版WinMM诊断，与串口工作台、Ozone调参和精简遥控放在同一程序。切入诊断会撤销遥控许可；已开启遥控时请求全设备失能，原串口连接可保留。不再单独发布手柄测试EXE；需要严格独立只读模式时运行 `DMDebugStation.exe --input-diagnostics`，该模式不注册串口、电机或Ozone控制命令。

1. 确认设备、Windows输入通道和日志路径。新版只读诊断使用WinMM独立轴，不经过gilrs标准手柄映射；失焦不暂停采集。WinMM可能仅给出驱动名称，USB VID/PID和UUID未知时显示“未提供”，不把制造商编号伪当USB身份。
2. 在“普通模式”逐项慢测：左杆四方向、右杆四方向、十字键、1～4、肩键、Select、Start及摇杆按下；每个动作后释放回中。
3. 点阶段标记“准备按Analog”，按物理Analog并记录LED变化；再点“Analog后重复测试”，重复同一套动作。Select另行标记前后测试，不能仅因按键名字推断它是模式键。
4. 与Windows `joy.cpl` 测试页对照X/Y/Z/Z旋转等通道：每轴显示Windows校准整数`rawValue`、声明`minimum..maximum`和归一化`value`。未反向、未加软件死区、未按实测端点自动放大；物理按钮只读按钮位图，POV另列，不把模拟轴解释成扳机。Code是当前API通道编号，不是通用物理键位。未产生变化的Analog等物理键可能仅由手柄内部处理，不能仅凭无事件判定损坏。
5. 完整事件自动写入界面显示的JSONL日志；把日志发回分析。页面最多展示最近200条，不等于完整记录。暂停记录不控制设备，切回继续后不会补造暂停期间事件。

此诊断仅支持Windows；每20ms读取WinMM校准状态并记录观察到的变化，不是USB HID报文抓取，也不能保证记录比采样周期更短的按键脉冲。轴归一化仅按系统声明量程线性换算，回中可能有一个整数单位的偏差。正式桌面遥控和诊断共享同一WinMM采集实现；诊断在独立日志线程运行，不将文件写入放进遥控采样路径。旧gilrs采集、手动绑定和遥控页重复原始面板已删除。

## HC-05类蓝牙串口与手柄遥控

链路为USB手柄→电脑上位机→蓝牙SPP虚拟COM→模块UART→STM32 USART1。当前协议和外设无需因透传而修改；桌面使用原生串口，便携网页使用Web Serial。当前用户手柄的Windows布局已确认，具体蓝牙模块、配对/Windows蓝牙驱动及无线延迟仍须现场确认。

1. 先断动力接线：模块TX接PA10/RX、模块RX接PA9/TX、GND共地；供电与逻辑电平按具体模块板卡确认，不把供电电压当作UART电平。模块必须双向透明传输二进制，通信模式为115200/8N1；AT配置模式的波特率不是透传波特率。
2. 在Windows完成蓝牙配对，确认模块的SPP COM口；如没有COM口，先解决模块/驱动，不假定BLE可直接使用。上位机选择实际端口并握手，核对四轮反馈在线。
3. 插入手柄，进入“手柄遥控”并选择设备即可预览，不需要填写编号或额外应用绑定。桌面使用Rust/WinMM，浏览器使用真实Gamepad API；遥控页仅保留设备、前后/左右/旋转三路输入条、Start状态和必要安全/调度状态，旧诊断由独立“输入诊断”页取代。未连接串口时也可观察输入预览，但它不是已发送速度或电机反馈。
4. 固定控制：左杆X/Y分别对应Windows code0/1，右杆X对应Z/code2；右杆Y对应Z旋转/code3，向上时数值降低，但完全不参与控制、回中或输入合法性门禁。Start是按钮10/零基code9；浏览器固定使用axes0/1/2和button9，不宣称其余API通道等同WinMM。左杆上推前进、右推右移；右杆右推顺时针旋转。
5. 先让三个控制轴回中并稳定释放Start，再重新按下：仅请求使能底盘0x40，四轮新反馈确认后才允许运动；不会使能六台位置DM或两台M2006。按下与释放均需连续稳定40ms，长按仅切换一次，10～20ms抖动不重复触发。径向中心死区0.12；死区外线性换算，手柄平移满幅合成0.4m/s（斜推也不超过），旋转满幅保持10deg/s，回中只发送零速并保持使能。
6. 再次有效按下Start向全部九个控制单元发失能，关闭无需摇杆回中。退出遥控页（含进入输入诊断）、失焦/隐藏、断柄、无效控制输入或超时均撤销许可；恢复不自动运动，重新开启必须稳定释放后再按。停止保留设备选择，重连/身份变化则清除选择。全体失能会释放关节/伸缩保持力，须先机械支撑重力负载。
7. 遥控速度使用最新值单槽，最快每100ms发一次，不积压旧杆位；250ms没有新鲜输入就退出。全部请求仍走唯一序号与单在途队列；停机优先，缺失应答不宣称停机成功。串口完全故障仍依赖下位机500ms门禁及正常CAN/电调，硬件急停不可替代。

手柄操作者平移上限为0.4m/s；固件及手动控制的既有1m/s能力、旋转10deg/s、轮速包络160rpm和启用前能力校验不变。用户已报告底盘手柄测试正常；本次仅调整手柄比例上限，更新后重新打开工作台生效，不修改或烧录STM32固件。实际运动仍须机械支撑、硬件急停和安全空间。

## Ozone直接内存调参

1. 启动支持Automation Socket的Ozone（参考工程使用V3.50，接口自V3.40提供），连接目标并加载与板上程序匹配、含调试符号的ELF；软件连接本机 `127.0.0.1:19200`，不会替你烧录、复位、暂停或运行CPU。
2. 打开Windows桌面上位机，切到“Ozone调参”页，连接Ozone并选择单台设备，读取当前参数。普通网页不能建立原始TCP，只显示入口说明，不伪造Ozone连接或写入成功。
3. 页面显示实际C++字段表达式、解析出的RAM地址、读回值、独立编辑草稿和单位；DM伸缩的这页使用内部输出轴deg/deg每秒，与串口工作台的mm不同，不再乘除传动比。
4. 明确允许直接写入后，编辑一个参数，点击该行的写入按钮。软件写活跃控制对象字段并逐项回读；需要保持设备重建时一致的配置副本会作为镜像地址一起写入。只有float32位值回读一致才显示成功。
5. 调整后再次读取确认。PID增益、输出限幅、M2006位置PD和轨迹配置均直接进入原对象，不使用邮箱或固件参数应用函数；不自动清除积分/微分历史、重新使能或重求当前曲线。M2006轨迹默认配置作用于下一条新曲线。
6. 导出保存当前读到的单台参数文件；导入只更新草稿，不自动写设备。重启后RAM修改消失，仍使用固件编译时的启动值。

本页按调试内存工具工作，**不提供参数物理范围、使能、运动或静止状态门禁**。它会绕过设备接口校验；多地址/镜像写入不是原子事务，控制中断可能读到中间值。失败可能已经部分写入，软件不自动回滚或重试，必须重新读取确认。写入保持力矩和限幅可能立即变化，先确认机械支撑、动力隔离与硬件急停。

地址从ELF符号解析，不固定C++类偏移；仅开放本工程的固定参数目录，检查RAM区域、类型、指针有效性及float32有限编码。M2006的 `std::optional` 轨迹必须已构造；ELF/编译器布局不匹配或Ozone无法解析成员时直接报错，不猜地址。Ozone页与串口工作台切换不会销毁串口通信引擎，原500ms串口失联保护仍保留。

## 开发、测试与构建

网页开发需要 Node.js 与 npm；运行现有回归测试使用 Node.js **24.14 或更高兼容版本**。Windows 桌面构建还需要 Rust 工具链、MSVC C++ 构建工具和 Windows SDK，运行时需要 WebView2。

```sh
git clone https://github.com/HITSZ-WTRobot/dmdebug-station.git
cd dmdebug-station
npm ci

# 启动开发页面
npm run dev

# 通信调度的确定性回归测试
npm test

# 类型检查、网页构建和便携单文件导出
npm run build:web

# Windows 桌面构建，同时更新根目录 DMDebugStation.exe
npm run build:all
```

`npm test` 使用 Node 内置测试框架；现有 TypeScript 参数属性通过实验性转换开关运行，会打印 Node 的实验性功能提示，不影响构建后的应用。依赖版本由 `package-lock.json` 和 `src-tauri/Cargo.lock` 记录。

修改源码后应重新构建对应入口，不要继续运行旧 EXE 或旧 HTML。`node_modules/`、`dist/`、`src-tauri/target/`、EXE 和日志被 Git 忽略；便携网页作为交付入口随源码提交。

## 通信与安全边界

- 协议为 64 字节定长帧、CRC-16/CCITT-FALSE、单请求停等。全设备广播收齐九台应答，四轮查询收齐四个轮位；序号匹配，最多一次同字节重试，不以新序号自动重发不确定的运动命令。
- 桌面版通信与手柄控制由Rust独立线程驱动，前端只传连接/命令/设备选择/页面许可意图并展示事件。串口只由一个Rust会话拥有，心跳、序号、CRC、重试、遥控最新目标与失能优先队列均在后端；页面渲染卡顿不再拖住通信定时。
- 浏览器版无本机Rust进程，保留Web Serial及内联Worker时钟，Gamepad API采样受页面生命周期影响。两条路径不同时拥有同一串口，不把浏览器限制当作桌面能力。下位机500ms门禁不放宽；系统休眠、进程停止、USB或真实无线故障仍无法靠PC保证硬实时或物理安全。
- 串口失联原因与 CAN 离线分开判断：配套修复版固件的串口结果 107 为 LinkFault，结果 1 为真正电机反馈离线。新心跳不自动恢复使能或旧目标。
- “停止 / 保持”不等于失能或硬件急停；断开串口、暂停图表、暂停 CPU 都不能保证机构停止。DM 当前电机端 CAN Timeout 为 0，仍须使用机械支撑及硬件急停。

当前49项Node与60项Rust回归通过，网页和Windows完整构建通过。覆盖固定三轴/Start、右杆Y和其他按钮不参与控制、方向/比例/严格合成限幅、40ms双向消抖、长按/抖动、回中/释放、断柄/失焦/通信撤销，以及既有协议、串口调度和Ozone回归。未沿用旧可编辑绑定契约。

本次实际运行合并后的Windows工作台及便携单文件网页，均识别到真实USB手柄；桌面WinMM获得X/Y/Z/Z旋转、12个物理按钮和POV，网页使用自身Gamepad API。实际选择设备并观察零输入预览，确认未使能时调度目标为零；切入新诊断页清除释放许可、保留连接选择且无串口停机伪错误。新版诊断IPC可用，旧配置IPC已移除；三路条形和新导航均已观察。未连接真实COM、未进行蓝牙/电机使能或带载联调。

此前Ozone专项验证记录（本次未重复该界面场景）：实际Windows程序经本机自有TCP模拟服务验证了桌面页→Tauri IPC→TCP→Ozone格式回复的整条路径，DM Kp写入并回读77.25，M2006速度Ki写入并回读0.125、位置PD Kp写入并回读6.5，镜像一致、单次授权自动撤销；切页串口演示持续收发且CRC/超时保持0。实际导入文件只填草稿，导出文件包含当时读值而非未写草稿。

本轮没有连接真实Ozone/J-Link、COM端口或电机，未写真实目标内存。TCP模拟只证明软件协议与交互路径；实际Ozone版本的C++符号解析能力、匹配ELF、运行态调试访问和实物响应仍需在安全条件下确认，不将模型、演示或编译成功表述为带载稳定或硬件安全。
